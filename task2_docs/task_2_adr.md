# Задание 2. Разработка сервиса отчётов BionicPRO

## 1. Цель решения

Пользователю BionicPRO необходимо предоставить возможность скачать отчёт о работе принадлежащего ему протеза. Данные для отчёта находятся в разных источниках:

- CRM хранит пользователей и связь пользователя с протезами;
- операционная PostgreSQL хранит техническую телеметрию протезов.

Формировать отчёт объединением этих источников во время пользовательского запроса нельзя: объём телеметрии постоянно растёт, а аналитическая нагрузка может ухудшить работу основной системы.

Предлагается следующее решение:

1. **Apache Airflow** по расписанию переносит данные CRM и телеметрии в ClickHouse.
2. **ClickHouse** хранит заранее рассчитанную витрину в разрезе пользователей и протезов.
3. **Reports API на Go** читает готовые строки витрины без сложных расчётов в реальном времени.
4. **Keycloak** подтверждает личность и роль пользователя.
5. **React UI** предоставляет кнопку скачивания собственного отчёта в CSV.

Доработанная архитектура представлена на
[`BionicPRO_C4_model.puml`](./BionicPRO_C4_model.puml).

## 2. Основные архитектурные решения

### 2.1. Аналитика

Операционные базы CRM и телеметрии остаются источниками данных, но пользовательские запросы отчётности к ним не обращаются. Для аналитики используется отдельная OLAP-база ClickHouse.

Такое разделение позволяет:

- не выполнять тяжёлые группировки в операционной PostgreSQL;
- независимо масштабировать хранение и обработку телеметрии;
- заранее проверять полноту данных;
- получать отчёт простым запросом по пользователю и периоду.

В учебном стенде отсутствующие внешние системы представлены двумя PostgreSQL-контейнерами: `crm_db` и `telemetry_db`.

### 2.2. ETL с использованием Apache Airflow

Реализован DAG `reports_etl` с почасовым расписанием:

```text
0 * * * *
```

DAG:

1. проверяет доступность источников;
2. переносит связи пользователей с протезами и новые события телеметрии в staging-слой ClickHouse;
3. объединяет события с владельцами протезов;
4. группирует показатели по пользователю, протезу и часу;
5. проверяет полноту и уникальность данных;
6. публикует витрину и продвигает `processed_until`.

Первый запуск обрабатывает всю доступную историю. Последующие запуски используют watermark и повторно обрабатывают небольшое двухчасовое окно, чтобы подхватывать опоздавшие события. Затронутый диапазон пересчитывается целиком, поэтому повторный запуск не создаёт дубликаты.

`catchup=False` предотвращает автоматический запуск всех пропущенных исторических интервалов, а `max_active_runs=1` исключает конкурентную публикацию одной витрины.

### 2.3. Витрина отчётности

Витрина `report_by_user_hour` содержит одну строку на пользователя, протез и час. В ней заранее рассчитаны:

- количество событий;
- среднее время реакции;
- 95-й перцентиль времени реакции;
- средний уровень заряда;
- время последнего события.

Таблица партиционирована по месяцу и отсортирована по:

```text
(user_id, period_start, prosthesis_id)
```

Такой порядок соответствует основному запросу Reports API. Объединение CRM и телеметрии, дедупликация и расчёт агрегатов уже выполнены Airflow.

Отдельная таблица `etl_state` хранит `processed_until` — конец последнего полностью подготовленного периода. Граница меняется только после успешного ETL и проверок качества.

### 2.4. Reports API и ограничение доступа

Реализован отдельный Go-сервис с эндпоинтом:

```http
GET /reports?from=<RFC3339>&to=<RFC3339>
Authorization: Bearer <access token>
```

По умолчанию API возвращает данные за 30 дней до `processed_until`. Максимальный диапазон ограничен 31 днём.

Перед обращением к ClickHouse сервис проверяет:

- подпись JWT по ключам Keycloak;
- `issuer` и `audience = reports-api`;
- срок действия токена;
- наличие роли `prothetic_user`.

Идентификатор пользователя всегда берётся из JWT claim `sub`. Если клиент передал другой `user_id`, сервис возвращает `403` до обращения к ClickHouse. Изменение URL поэтому не позволяет получить данные другого владельца.

Если запрошенный период находится после `processed_until`, API возвращает `422` и сообщает доступную границу. Неполный период не выдаётся как готовый отчёт.

Reports API использует отдельную учётную запись ClickHouse с правом `SELECT` только для витрины и `etl_state`.

### 2.5. Получение отчёта через UI

В React UI добавлена кнопка «Скачать отчёт», доступная после входа через Keycloak.

При нажатии UI:

1. обновляет access token;
2. вызывает `GET /reports` с Bearer-токеном;
3. не передаёт `user_id`;
4. преобразует ответ API в CSV;
5. скачивает файл `bionicpro-report-YYYY-MM-DD.csv`;
6. показывает количество строк и границу обработанных данных.

### 2.6. Моковые данные

Так как внешние CRM и поток телеметрии недоступны, для демонстрации создан воспроизводимый набор данных:

- 6 пользователей с теми же UUID и ролями, что и в Keycloak;
- 4 протеза у трёх пользователей с ролью `prothetic_user`;
- 34 560 событий за 30 дней.

Совпадение CRM `user_id` и Keycloak `sub` позволяет проверить весь сценарий от аутентификации до получения собственного отчёта.

| --------------------------- | ------------------------------------------------------------------- |

## 4. Как проверить решение

### 4.1. Запуск

Из корня репозитория выполнить:

```bash
docker compose up --build -d
docker compose ps
```

После запуска доступны:

- UI — <http://localhost:3000>;
- Reports API — <http://localhost:8000>;
- Keycloak — <http://localhost:8080>;
- Airflow — <http://localhost:8081>.

### 5.2. Подготовка витрины

Открыть Airflow, войти как `admin / admin`, найти DAG `reports_etl` и запустить его вручную. Все задачи DAG должны завершиться со статусом `success`.

Витрина также будет обновляться автоматически каждый час.

### 5.3. Получение отчёта

1. Открыть <http://localhost:3000>.
2. Нажать «Войти».
3. Войти как:

   ```text
   Логин:  prothetic1
   Пароль: prothetic123
   ```

4. Нажать «Скачать отчёт».

Должен скачаться CSV только с протезами `BP-HAND-001` и `BP-HAND-004`. В UI отобразятся количество строк и время `processed_until`.

### 5.4. Проверка ограничения доступа

Выйти и войти как пользователь без роли отчётности:

```text
Логин:  user1
Пароль: password123
```

При попытке скачать отчёт API должен вернуть `403`, а CSV не должен создаться.

Запрос без аутентификации:

```bash
curl -i http://localhost:8000/reports
```

должен вернуть `401 Unauthorized`.
