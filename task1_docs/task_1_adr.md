# Задание 1. Управление учётными данными пользователей BionicPRO

## 1. Цель решения

Нужно унифицировать вход в приложения BionicPRO, не создавая центральное международное хранилище персональных данных и не передавая во фронтенд `access`- и `refresh`-токены, полученные от удостоверяющих служб.

Предлагается следующие решение:

1. **Identity Broker** — региональный Keycloak скрывает различия между внешними IdP и выдаёт внутреннюю идентичность BionicPRO.
2. **Backend for Frontend (BFF)** — единственный OAuth-клиент приложения. BFF получает и обновляет токены на сервере, а фронтенду выдаёт только   непрозрачный идентификатор сессии в защищённой cookie.

## 2. Основные архитектурные решения

### 2.1. Отдельный контур в каждой стране

В стране каждого представительства разворачивается региональный экземпляр:

- фронтенда приложения;
- BFF;
- Keycloak;
- Keycloak DB;
- серверного хранилища сессий;
- API и хранилищ персональных и медицинских данных.

Региональный Keycloak подключается только к разрешённым в этой стране внешним IdP. Внешняя служба остаётся владельцем паролей, факторов MFA и исходной учётной записи.

Пользователь попадает в свой регион по региональному домену или выбору страны до начала аутентификации. Для добавления страны разворачивается ещё один экземпляр того же контура и настраиваются местные IdP. Глобально допустимо хранить только конфигурацию маршрутизации без пользовательских идентификаторов, профилей и медицинских данных.

Такое размещение обеспечивает локализацию:

| Данные                                                                     | Место хранения                         |
| -------------------------------------------------------------------------- | -------------------------------------- |
| Пароль, MFA и исходный профиль                                             | Внешний IdP в стране представительства |
| Минимальная связка `issuer + subject -> internal_user_id`, роли и согласия | Региональная Keycloak DB               |
| Серверная сессия и внутренние токены Keycloak                              | Региональное хранилище сессий BFF      |
| Персональные и медицинские сведения, связь пользователя с протезами        | Региональная БД BionicPRO              |

В Keycloak включается минимальное JIT-provisioning: хранится неизменяемая связка `iss + sub` с внутренним `user_id`, но не пароль внешней системы. Email и ФИО нельзя использовать как устойчивый ключ. Запрашиваются только необходимые scopes/claims. Сохранение токенов внешнего IdP после завершения входа и broker token exchange отключаются.

### 2.2. Keycloak как Identity Broker

Keycloak предоставляет BionicPRO единый OIDC-интерфейс и преобразует атрибутыразных IdP в канонические claims. Поддерживаются:

- OIDC-провайдеры;
- SAML 2.0-провайдеры;
- при необходимости — локальные государственные или корпоративные службы через отдельный адаптер в региональном контуре.

Набор ролей BionicPRO и права на протезы не принимаются напрямую из внешнего IdP. IdP подтверждает личность, а роли и связь `internal_user_id -> prosthesis_id` определяются внутри BionicPRO. Это не позволяет ошибочно выданному внешнему атрибуту предоставить доступ к чужому протезу.

### 2.3. BFF как конфиденциальный OAuth-клиент

Фронтенд больше не является OAuth-клиентом и не обращается к Keycloak API напрямую. Конфиденциальным клиентом регистрируется BFF:

- redirect URI задаётся точным адресом callback BFF;
- client secret или закрытый ключ хранится в менеджере секретов;
- wildcard redirect URI, implicit flow, password grant и прямой token exchange отключаются;
- для входа используется OIDC Authorization Code; `state` и `nonce` обязательны, PKCE S256 может применяться как дополнительная защита.

После входа BFF создаёт серверную сессию и возвращает браузеру только cookie:

```text
__Host-bionicpro-session=<случайный идентификатор>;
Secure; HttpOnly; SameSite=Lax; Path=/
```

В cookie нет JWT, персональных данных или токена IdP. JavaScript не может
прочитать cookie из-за `HttpOnly`. Для изменяющих состояние запросов BFF
дополнительно проверяет CSRF-токен и `Origin`.
